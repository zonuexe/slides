Page 25

Common Gateway Interface

  • HTTPサーバーがリクエストを受ける度にプロセスを起動する
  • リクエストヘッダが環境変数に、リクエストボディがstdinに入力される
  • プログラムがstdoutに出力したものがヘッダ・ボディになる
  • 標準入出力と環境変数さえ読み書きできれば言語はなんでもいい
  • 現代でもAWKとかBashとかでCGIを書く人がいたりする

CGI言語としてのPerl/PHP

  • CGI処理に求められているのは本質的にはHTTPヘッダとボディ出力
  • Perl: cgi-lib.pl や CGI.pm などのライブラリでの「出力サポート」
  • 気をつけて使わないとHTTPヘッダが壊れる
  • PHP: HTTP出力そのものが言語コアに統合されている
  • 言語ランタイムがHTTPメッセージの入出力を担保してくれる
  • CGIではない環境でもCGIスタイルのスクリプトが基本

Page 33

レンタルサーバにファイル転送するだけでデプロイ完了(CGI Perl, PHP)

Page 34

Web言語としてのインターフェイス

  • CGIはリクエストごとにプロセスをフォークするのでパフォーマンスが出ない
  • リクエストごとに状態がすべてリセット、グローバル変数などは問題がない
  • 90年代のアプローチ： Apacheモジュールとして組み込む
  • mod_perl, mod_ruby: デフォルトでは同じプロセスで動き続ける
  • mod_php: リクエストごとに状態が破棄されるCGI互換モードがデフォルト

Page 35

プロセス内サーバインターフェイス

  • CGIのようなstdin/stdoutではなく、同じ言語の関数レベルの仕様
  • 2003年 WSGI (Python) | 2007年 Rack (Ruby)
  • 2009年 PSGI / Plack (Perl) @YAPC::Asia 2009 miyagawa
  • CGI世代の「スクリプト」と「フレームワーク／アプリケーション」の分水嶺
  • 分離するとユニットテストが書きやすくなるなどのメリットは大きい
  • PHPにも共通インターフェイスはあるが、必須ではなく断絶を経験しない

ハッシュ (連想配列)

  • ハッシュテーブルというデータ構造はPerl以前からあった
  • 連想配列(っぽいもの)を実現するデータ構造はハッシュ以外にもあった
  • Lisp系は連結リストベースの連想リスト・プロパティリストというものがある
  • ライブラリやユーザー定義のデータ構造として流行らせたのはPerlでは…？
  • 現代ではJSON(object)を経て、どんな言語でも扱えることが普通

Page 41

正規表現

  • 正規表現はPOSIX基本正規表現、POSIX拡張正規表現がある…が、Perl正規表現はPOSIX系と互換性がない？
  • 記号の意味が大きく違うというわけではないが、\ エスケープが反転
  • 現在普及している多くの『正規表現』は多かれ少なかれPerl風
  • Perlの全機能が網羅されているものはないが、しばしば実用される範囲での互換性はあると思う ／ PCREはPerl完全互換ではない

Page 42

CPAN (Comprehensive Perl Archive Network)

  • Perlで書いたライブラリを共有する仕組み
  • ざっくりRubyGems, NPM, PyPI, crates.ioなどに繋がるもの
  • READMEに書くべき内容やテストの標準化など今も尊ばれるべきもの
  • Perl界隈でCPANオーサーがリスペクトされる文化が大好き
